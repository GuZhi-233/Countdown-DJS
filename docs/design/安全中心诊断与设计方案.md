# 插件安全中心：权限、拦截通知与自由度设计

基线：`djs_pyqt6.py`（约 3.1 万行）。本文为只读诊断，未修改主程序、`data/` 与 `plugins/`。
所有行号对应分析时的文件快照；另一会话正在编辑同一文件，行号可能有小幅漂移，函数名稳定。

## 0. 摘要

| 编号 | 结论 | 关键证据 |
| --- | --- | --- |
| 一 | 权限校验**没有**被 `plugin_monitor` 劫持。开关只控制"放行记录"写不写。真正造成"没授权也能读"的是授权数据被自动赋值、以及检测层多个静默 `return`。 | `audit_hook` 5453-5548；隔离复现见 1.2 |
| 二 | 拦截提示是系统托盘气泡，程序里没有实例集合、没有队列、没有关闭句柄、没有节流，也没有 `messageClicked`。插件通知与安全拦截共用同一个气泡出口。 | 4174-4179、4774-4781、29086-29101 |

## 1. 问题一：权限校验与"详细记录日志"开关

### 1.1 判定分支的真实嵌套关系

`PluginManager._install_audit_hook()` 内定义了 `audit_hook`（5453）与两个闭包 `_record`（5470）、`_deny`（5482）。实际执行顺序如下（按代码行序归纳，非原文）：

```
audit_hook(event, args):
  5454  _audit_guard.active        -> return
  5456  _audit_suppress            -> return
  5458  security_center_disabled   -> return
  5460  event 不在 _MONITORED_EVENTS -> return
  5462  plugin = _plugin_context.current_plugin
  5464  plugin = _plugin_from_stack()
  5465  plugin 为 None             -> return
  5467  disabled / 5468 granted = effective_permissions(plugin)

  5499  event == "import"    : 只查 _BLOCKED_MODULES，否则 return
  5506  受保护文件            : _deny
  5509  改写/删除插件源码      : _deny
  5517  event 在 _ALWAYS_DENY : _deny
  5519  event == "open"      : 5521 内部文件 -> return
                              5528 disabled -> _deny
                              5530 写插件源码 -> _deny
                              5533 无 FILE_WRITE -> _deny
                              5536 无 FILE_READ  -> _deny
                              5538 _record(..., is_file=True)
  5540  其它事件              : perm = AUDIT_POLICY[event]
                              5545 权限不足 -> _deny
                              5547 _record(..., is_file=event in _FILE_EVENTS)
```

`_deny` 的调用在 5528、5530、5533、5536、5544、5546，全部位于 `_record` 之外；`_record` 内部的 5474 只包住两行写记录：

```
5474  if is_file or manager.app.plugin_monitor:
5475      append_sensitive_log(...)
5476      append_security_event(..., "allow", ...)
```

所以"权限判定被嵌在日志分支内"这一假设**不成立**。`plugin_monitor` 的布尔值不参与任何 `_deny` 判定。

### 1.2 隔离复现（加载真实模块，不启动 GUI）

用真实 `PluginManager` + 伪 app，临时插件目录，插件实例 `permissions=0`、`_auth_perms=0`，分别调用内置 `open`、`pathlib`、`os.listdir`：

| 用例 | plugin_monitor | 结果 | 事件数 |
| --- | --- | --- | --- |
| 内置 `open` 读 data_dir 内文件 | False | 拦截：`无读取文件权限` | 3 |
| 内置 `open` 读同一文件 | True | 拦截：`无读取文件权限` | 3 |
| `pathlib.Path.read_text` 读 data_dir 内文件 | False | **放行** | **0** |
| `pathlib.Path.read_text` 读 data_dir 外文件 | False | 拦截 | 3 |
| `os.listdir(data_dir)` | False | 拦截 | 3 |
| `_audit_suppress=True` 后读任意文件 | False | **放行** | **0** |

结论：开关切换不改变拦截结果；放行发生在别的分支上，且在放行时**连事件都不记**。

### 1.3 真正会让"未授权也放行"的入口

按危害排序。

1. 授权数据有第二事实源，缺键时回落到插件自报值
   `effective_permissions()`（5645-5657）：`_auth_perms` 里没有该文件名时，直接返回 `plugin.permissions`。
   `set_permissions()`（5659-5669）同时写两处；但下列代码只写 `plugin.permissions` 或提前把它填成申请值：
   - 宿主加载时清单权限直接落到实例：7492-7496 `instance.requested_permissions = masked; instance.permissions = masked`。
   - 恢复状态时无 `permissions` 键但 `enabled=True`：28764-28765 直接授予 `requested_permissions`，没有任何询问。
   - 恢复/重载用 `force=True` 启用：28767、5943；`enable_plugin` 里 `force=True` 跳过 6028 的询问，6051-6052 用 `locked_before = effective_permissions()`（此时已被清单值填充）回写，等于确认。
   - 例外分支 5939-5940：读配置失败时授予 `requested_permissions`。

2. 询问文案与实际授予范围不一致
   6029-6042 只把 FILE_READ / FILE_WRITE / NETWORK / COMMAND 四项写进提示文字，用户点"是"后执行 `set_permissions(plugin, perms)`，`perms` 是完整 `requested_permissions` 位图，可含 `DANGEROUS_EVAL`、`REGISTRY`、`PROCESS_SPAWN`、`CLIPBOARD`、`ENV_READ`、`UI_INJECT` 等未在提示中出现的权限。

3. 检测层无法指认插件时直接放行
   `plugin is None` 时 5465-5466 直接 `return`，既不拦也不记。会走到这里的场景：
   - `_plugin_from_stack()`（5578-5602）只扫描 60 帧，且必须命中 `self.plugins` 中 `filename` 相同的实例；
   - 插件用 `exec`/`eval` 执行字符串时帧文件名为 `<string>`，5578-5602 里 `fname.startswith('<')` 被跳过；
   - `_plugin_context` 是 `threading.local`，非经 `_install_thread_context()` 补丁创建的线程拿不到当前插件；
   - 插件通过 `import` 第三方模块间接读写，帧链里可能先命中数量上限或非插件文件。

4. data_dir 白名单的判定只看调用者的上一层
   `_is_app_internal_file()`（5437-5451）里 `sys._getframe(2)` 取得的是"触发 `open` 的那一帧"。经 `pathlib`、`json`、`csv`、`logging` 等标准库包装后，这一帧是标准库文件，不是插件文件，于是 5449 返回 True，5521 直接 `return` 放行。复现表第 3 行就是这个路径。同时因为 5521 在 `_record` 之前，这次访问也不会进任何记录。

5. `_audit_suppress` 可以整段关掉钩子
   进程内 5752 置 True、5911 复位；宿主侧 7398 置 True、7511 复位。两段都不在 `try/finally` 里：进程内的 5755 `sorted(os.listdir(self.plugin_dir))` 若抛异常，或宿主 7468 之后清单读取抛异常，标志就停在 True，此后整个进程的审计钩子在第 5456 行静默返回。复现表最后一行验证了效果：读任意路径都放行、0 事件。

6. 全局开关的持久化早退
   5458 `security_center_disabled` 为真时钩子直接返回。该值持久化在 `countdown_config.json`（当前快照 `false`），关闭安全中心后必须重新开启才会恢复拦截。这不是漏洞，但会让"昨天还好、今天全放行"复现成"开关问题"。

### 1.4 为什么现象看起来像"开日志才拦截"

开关确实改变可观察面，三处：

- 5474：`os.listdir` / `os.scandir` / `os.stat` 这类事件在 `AUDIT_POLICY`（4204 起）里，但不在 `_FILE_EVENTS`（4191-4195）。`is_file=False` 时只有 `plugin_monitor=True` 才写"放行记录"。同一操作在关闭时安全中心里一片空白。
- 5476 → 29079：`_maybe_alert_runtime_risk` 只在 `append_security_event(kind="allow")` 时触发；关闭开关后 allow 事件根本不产生，高风险提醒也不会出现。
- 6635：宿主进程的 `_HostShimApp.plugin_monitor` 硬编码 `True`，父进程的开关不回传宿主。进程内加载与宿主加载两种模式下，开关的实际效果不同。
- 6636：宿主 `plugin_prompt_on_deny=False`，拦截气泡改由 IPC 转到父进程（6650-6651 → 4814-4824）再弹，插件实际运行在宿主时，"弹窗"总比拦截晚一拍。

因此：**开关决定"看不看得见"，不决定"拦不拦"。** 如果实际测试中确实存在"关掉开关就放行"的可复现差异，最可能的落点是 1.3 的第 1、3、5 条，需要在临时副本上给 5453-5468 加命中计数确认，而不是改日志开关。

### 1.5 修复方案（P0）

1. 单一事实源。`_auth_perms` 为唯一权威，`plugin.permissions` 降级为展示缓存；`effective_permissions` 缺键返回 `NONE`，不再回落（5645-5657）。`set_permissions` 之外禁止写 `plugin.permissions`。
2. 删除自动授权。28764-28765、5939-5940、7492-7496 改为只写 `requested_permissions`；恢复时缺 `permissions` 键的插件一律停在 `NONE` 并在安全中心标"待确认"。`force=True` 只跳过"是否启用"，不跳过授权询问（6028）。
3. 询问与授予同集合。提示文案由 `_PERM_LABELS`（3997-4016）逐项生成，`set_permissions` 收到的位图必须与文案完全一致。
4. 检测层 fail-closed。事件路径在插件目录内却无法匹配实例时，按 `unknown-plugin` 记录并拒绝敏感项（FILE_READ/WRITE/DELETE、NETWORK、COMMAND），不要 5465 静默返回。
5. 白名单判定改为"栈内是否存在插件帧"。`_is_app_internal_file` 复用 `_plugin_from_stack` 的扫描逻辑，而不是只看 `_getframe(2)`；`pathlib` 复现用例必须转为拦截。
6. 抑制窗口只覆盖加载期，并且 `try/finally`；7398-7511 包一层。建议再加一个"加载超过 N 秒自动复位"的看门狗，防止异常路径长期失守。
7. 记录与判定彻底解耦。`audit_hook` 对所有命中事件无条件调用记录入口，是否落盘由 `append_sensitive_log`/`append_security_event` 内部按 `plugin_monitor` 过滤；`block` 事件永远写入。
8. 宿主清单权限不要写 `instance.permissions`，去掉 `mp & 0x0F` 截断（7494）。

### 1.6 验收用例

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | `plugin_monitor=False`，无 FILE_READ，内置 `open` | 拦截，记录 block |
| 2 | 同上，`pathlib.Path.read_text` 读 data_dir | 拦截，记录 block |
| 3 | 无 FILE_READ，`exec` 字符串里 `open` | 拦截，标记 unknown-plugin |
| 4 | 状态文件无 `permissions` 键，`enabled=True`，重启 | 不拦截放行；安全中心显示"待确认" |
| 5 | 清单声明 `permissions: 15`，用户从未确认 | 不自动获得读权限 |
| 6 | 模拟加载异常后继续运行 | 审计钩子仍生效（`_audit_suppress` 回到 False） |
| 7 | 撤销 FILE_READ 后宿主内插件读文件 | 立即拦截（grants 已下发） |

## 2. 问题二：拦截弹窗关不掉

### 2.1 调用链与实例管理现状

```
拦截发生
  _deny (5482-5497)
    -> notify_security_denied (29096-29101)      [plugin_prompt_on_deny 为真时]
      -> _show_tray_warning (29086-29094)
        -> QTimer.singleShot(delay, showMessage)
          -> tray.showMessage(..., 4000) (29091)

宿主内拦截
  _HostShimApp.notify_security_denied (6650-6651)
    -> send_event("denied") -> 父进程 _apply_remote_event (4814-4824)
      -> 同一个 notify_security_denied

插件主动通知
  PluginAPI.show_notification (4174-4179)
  HostPluginAPI.show_notification (6776-6777) -> "notify" (4774-4781)
    -> 同一个 tray.showMessage，无权限校验、无频率限制、无来源校验
```

`notify_security_denied` 只做一件事：判断当前是不是主线程（29097-29098），然后调用 `showMessage`。没有实例集合、没有去重键、没有取消句柄、没有冷却时间。

### 2.2 成因

1. **没有"实例"可关。** `QSystemTrayIcon.showMessage` 是系统通知 API，每次调用生成一条独立 toast，Qt 不提供关闭已显示 toast 的接口。程序也没有保存任何返回值或引用，所以"关闭"在代码层面不存在。
2. **无节流、无合并。** `_deny` 每拦截一次就调用一次通知；插件在循环里读文件可以一秒触发几十次。`_show_tray_warning` 用 `singleShot(0)` 立即排入事件循环，形成通知风暴。
3. **Windows 通知中心累积。** Win10/11 的 toast 超时参数不完全生效，未点击的条目留在操作中心；下一次 `showMessage` 不会清掉上一条。用户看到的是"关一个、下面还有、 continually 再弹"。
4. **点击无响应。** 全文件只有 `tray.activated`（27635），没有 `messageClicked` 连接。点击气泡既不关闭也不跳转，用户只能等自动消失或去操作中心手动清。
5. **主线程过滤导致顺序不可控。** 非主线程直接 `return`（29097）；宿主拦截经 IPC 到父进程后才弹，密集拦截与 UI 事件交错，延迟不均匀。
6. **插件通知与安全通知同管道。** 4774-4781 连 `_host_plugin_ok` 都没校验，任何插件都能无限调用；用户无法区分哪条是拦截、哪条是插件广告。这一条会让"关了又弹"看起来像安全系统在刷屏。

### 2.3 修复架构：`SecurityNoticeCenter`

一个进程内单例，替代直接调用 `showMessage`。

- 数据结构
  - `NoticeCard`：`{id, plugin, perm, action, target, count, first_ts, last_ts, shape: single|summary}`
  - `_active: list[NoticeCard]`，最多 3 张，超出时把最旧的合并成汇总卡
  - `_pending: dict[(plugin, perm, reason)] -> NoticeCard`，200ms 聚合窗口
  - `_muted: dict[(plugin, perm)] -> 解除时间`
- 接口
  - `push_denial(plugin, perm, action, target, reason)` 由 `_deny` 调用
  - `push_summary(plugin, perm, count)` 由聚合器生成
  - `dismiss(card_id)` 必须从 `_active` 删除并 `deleteLater`
  - `dismiss_all()`
  - `mute(plugin, perm, seconds)`
- 形态切换条件
  - 同一 `(plugin, perm)` 在 1 秒内出现 ≥2 次，或全局 1 秒内 ≥3 条 → 汇总卡；
  - 单条事件 → 单卡；
  - 汇总卡标题固定为"已自动处理 N 项"，展开后按 `(plugin, perm)` 分组，每组一行"插件名 · 动作 ×N"。
- 关闭语义
  - 卡片右上角关闭 → 只移除该卡，并把这组事件写入审计（kind=block）；
  - 汇总卡的关闭 → `dismiss_all()`；
  - 卡片点击 → 打开安全中心"拦截记录"标签并定位该插件。
- 与托盘的关系
  - 默认走应用内卡片；托盘气泡仅在 `QApplication.activeWindow()` 为空、应用被最小化到托盘、或用户开启"系统通知"时作为兜底；
  - 不再直接调用 `tray.showMessage`，统一经 `SecurityNoticeCenter`，从源头解决"关不掉"。
- 插件通知
  - 走同一中心，`source=plugin`，每插件每分钟 3 条上限，超限丢弃并记审计；
  - 标题前缀固定为插件名，避免与"插件安全中心"混淆。

### 2.4 验收标准

| # | 操作 | 期望 |
| --- | --- | --- |
| 1 | 1 秒内触发 20 次拦截 | 1 张汇总卡，计数 20 |
| 2 | 点击关闭 | 卡片消失且 `_active` 为空，操作中心无新增条目 |
| 3 | 同一插件连续 50 次 `show_notification` | 最多 3 条，其余记审计 |
| 4 | 深/浅主题、100%/150% 缩放、多屏 | 位置在可用区右下，不越界 |
| 5 | 全屏倒计时运行中触发拦截 | 卡片可见且可关闭 |

## 3. 问题三：仿火绒的安全中心与自由度设计

### 3.1 现状盘点

| 结构 | 位置 | 现状 | 问题 |
| --- | --- | --- | --- |
| `PluginPermission` | 3976-3994 | 18 个 `auto()` 位 | 位定义齐全，但没有分级 |
| `_PERM_LABELS` | 3997-4016 | 18 项中文名 | 只用于列表展示 |
| `_PERM_NAMES` | 4258-4268 | 只有 9 项 | `_deny` 提示对另外 9 位回退成"所需权限"，用户看不懂被拦了什么 |
| `AUDIT_POLICY` | 4204-4257 | 事件到权限位映射 | `NETWORK` 合并了 HTTP/SOCKET；`FILE_WRITE` 承担删除 |
| `_auth_perms` | 4362 | 文件名到 int 的运行时权威表 | 与 `plugin.permissions` 双写，存在第二事实源 |
| `plugin_states` | 配置文件 | `{enabled, limited, permissions}` | 只有位图，没有授权范围、来源、时间、拒绝记录 |
| 安全中心 | 26997-27560 | 7 个标签：拦截/放行/文件操作/插件权限管理/敏感记录/插件日志/防护管理 | 无概览、无按权限视图、无白名单、无撤销入口 |
| 权限编辑 | 30683-30716 | 4 个复选框，保存时重建位图 | 其余 14 位在保存瞬间被抹掉 |
| 插件详情 | 30582-30586 | 只显示 4 项权限 | 用户看不到插件实际拥有什么 |
| 运行时评估 | 6119-6153 | `_security_events` 现算分 | 数据只在内存，重启清零；关闭 `plugin_monitor` 后 allow 事件不产生，评分偏低 |

### 3.2 权限粒度重划

三档定义：

- H（硬拦）：不可通过"点一次允许"获得；只能通过安全中心显式开启，且多数应保持不可开启。
- A（授权）：默认拒绝，首次触发询问，可记住决定。
- N（提示）：不拦，只记录/提示，避免把常用能力做成摩擦。

| 权限位 | 当前行为 | 建议档位 | 说明 |
| --- | --- | --- | --- |
| FILE_READ | H 按路径 | A + 范围 | 插件私有目录与只读资源目录归 N；其它路径 A，按目录授权 |
| FILE_WRITE | H | A + 范围 | 插件私有目录 N；系统路径 A |
| FILE_DELETE | 与 FILE_WRITE 合并 | H（保护对象）/ A（私有目录） | 删除配置、插件源码、程序目录永远 H |
| NETWORK | H | A | 出站 http/socket 合并授权，保留域名白名单 |
| NETWORK_HTTP | 未单独使用 | A | 白名单域名归 N |
| NETWORK_SOCKET | 未单独使用 | H | 监听端口（`socket.bind`）必须单独确认 |
| COMMAND | H | H | `os.system`、`subprocess` 不在"低摩擦"范围 |
| COMMAND_EXEC | 未单独使用 | H | `os.startfile`、`ctypes` 系列 |
| PROCESS_SPAWN | 未单独使用 | H | 与 COMMAND 同级 |
| CLIPBOARD | 未使用 | A | 读剪贴板按次询问，写剪贴板 N |
| SYSTEM_INFO | 未使用 | N | 基础信息只记录；主机名/用户名等敏感项按 A |
| NOTIFICATION | 未使用 | N | 走 `SecurityNoticeCenter`，限频即可 |
| UI_INJECT | 未使用 | N（仅 API） | 注册控件/设置面板已有 API 边界，不放开任意 QWidget 注入 |

### 3.3 授权交互

首次询问（A 档触发，单次合并）：

```
[插件] x.py 想要 读取文件
目标：C:\Users\...\Documents\a.txt
[允许一次] [允许本次会话] [永久允许] [拒绝并记住]
[ ] 同时允许该目录下的文件
```

- 作用域模型
  - `once`：只放行当前这一次调用，不写配置；
  - `session`：写入 `PluginManager._session_grants`，进程退出即失效，插件禁用时清空；
  - `persistent`：写入 `plugin_states`，带 `scope`、`targets`、`granted_at`；
  - `deny` + 记住：写入 `denied` 列表，后续同权限直接拒绝且不再弹窗（可在安全中心撤销）。
- 存储建议（保持向后兼容）
  - 继续用 `plugin_states[filename]["permissions"]` 存位图，供宿主与旧逻辑读取；
  - 新增 `plugin_states[filename]["grants_v2"]`：
    ```
    [{"perm":"FILE_READ","scope":"persistent","targets":["D:/notes"],
      "granted_at":"2026-11-06T18:00:00"}, ...]
    ```
  - 派生规则：`permissions = OR(grants_v2 中 persistent/session 的 perm)`。位图是缓存，明细是事实源。
- 撤销入口
  - 安全中心"插件权限管理"每行末尾"撤销全部"；
  - 展开行内逐项开关，关闭即写一条撤销审计；
  - 托盘右键菜单加"安全中心 → 撤销最近一次授权"。
- 白名单
  - 路径白名单：插件私有目录 `data/plugin_data/<filename>/` 默认加入，读写免除 FILE_READ/FILE_WRITE 询问；
  - 域名白名单：`plugin_states[filename]["hosts"]`，命中的 HTTP 请求归 N；
  - 全局白名单只允许"已签名 + 用户二次确认"，不接受未签名插件。
- 会话时效
  - `session` 授权随插件禁用、重载、宿主重启失效；这一点必须写进帮助文档，避免用户以为会持久。

### 3.4 批量拦截的呈现

聚合算法：

```
on_denial(record):
  key = (plugin, perm, action)
  bucket = pending.get(key) or new
  bucket.count += 1; bucket.last_ts = now
  debounce(200ms, flush)
flush():
  if 单个 bucket 且 count == 1: 单卡
  elif count >= 2 或 1 秒内 pending 总数 >= 3: 汇总卡
  同一 key 已存在 active 卡: 原地更新计数，不新建
```

两种形态：

- 单卡：图标 + "已拦截「x.py」读取文件" + 目标（截断 60 字符）+ 原因 + 四个动作按钮。
- 汇总卡："已自动处理 17 项" + 副标题"读取文件 ×12、网络 ×5" + 展开/收起 + 关闭。展开后每行可单独"查看详情"。
- 计数口径：一次被拦操作计 1 项；同一调用因重复触发只计首次（审计里仍全量记录）。
- 冷却：同一 `(plugin, perm)` 60 秒内最多弹 1 次单卡或 1 张汇总卡；期间只累加计数。
- 静音：卡片提供"本插件今日不再提示"，写入 `_muted` 并记审计。

### 3.5 安全中心界面结构

入口：设置 → 插件管理 → 安全中心（现有 `btn_security`，29999）；托盘菜单增加"安全中心"。

标签调整为 6 个：

1. 概览：全局开关（启用插件系统 / 详细记录 / 拦截提示）、今日拦截数、授权数、待确认插件、最近 10 条拦截。
2. 拦截记录：现有 `tree_block`（时间/插件/事件/目标/原因），新增"放行一次""永久放行""查看详情"。
3. 放行记录：现有 `tree_allow`，增加"撤销该授权"。
4. 插件权限：双视图切换。
   - 按插件：插件名 / 版本 / 状态 / 已授权（按档位分组） / 待确认 / 风险分 / 最近活跃。
   - 按权限：权限名 / 档位 / 授予插件数 / 最近使用 / 被拦次数。
5. 白名单：路径与域名两组列表，支持添加/删除/有效期。
6. 防护管理：保留现有开关（27194 起），补"审计保留天数""通知频率上限"。

操作定义：

| 操作 | 作用域 | 写入 |
| --- | --- | --- |
| 允许一次 | 单条记录 | 不写配置，`_session_grants` 加一次性令牌 |
| 允许本次会话 | 插件 + 权限 | `_session_grants` |
| 永久允许 | 插件 + 权限（可带目录） | `grants_v2` |
| 撤销 | 插件 + 权限 | 删除 `grants_v2` 条目，重算位图，下发宿主 |
| 加入白名单 | 路径/域名 | `hosts` 或 `paths` |
| 查看详情 | 单插件 | 该插件全部 `_security_events` 时间线 |

审计持久化：新增 `data/security_audit.jsonl`，按天轮转，保留 7 天，内存只保留最近 2000 条。当前 `_security_events` 上限 800（29077-29078）且不落盘，重启后风险分归零（6119-6146），这是"同样操作今天拦、明天不拦"的另一来源。

### 3.7 提升自由度的分级建议

| 级别 | 内容 | 改动面 | 风险 | 前置 |
| --- | --- | --- | --- | --- |
| L0 | 现状：18 位全硬拦，提示 4 项 | 无 | 无 | 无 |

# 权限模型：可解释性、自省与降级设计方案

基线：`djs_pyqt6.py`（约 3.4 万行，20 位权限，`permissions_v2` + `grants_v2`）。
本文为只读分析产物，本轮未修改任何代码、未改版本号。
行号对应分析时快照；另一路正在改同一文件（悬浮窗透明），实现前需按函数名重新定位。

---

## 0. 结论摘要

当前模型的问题不是“权限位不够多”，而是**判定结果只有一句话，没有结构**。插件拿到的失败信号是 `PermissionError("插件 'x' 无写入文件权限")`，无法区分“没声明 / 没授权 / 你点了拒绝并记住 / 这个目录是保护区 / 这一项永远不开放 / 根本没识别出是我”。用户侧同理：`FILE_WRITE` 已授权但写某个目录被拦，界面只说“无权限”，不说拦在哪一层。

本方案的核心是三个决定：

1. **判定与副作用分离**：抽出一个无副作用的纯评估器 `evaluate(...) -> Decision`，审计钩子、`require_permission`、控件密封、插件预检全部复用同一份判定。这是“结构化拒绝”和“申请前可查”的共同地基，也是避免“预检说能、实际又被拦”的唯一办法。
2. **拒绝变成数据**：新增 `PluginPermissionDenied(PermissionError)`，携带 `code / permission / capability / scope / denied_by / layer / retryable / unlockable / retry_after_ms`，文案保持不变以兼容旧插件。
3. **失败可降级**：新增 `api.can()` 预检、`api.capabilities()` 快照、`api.on_denial()` 回调、`api.call_with_fallback()` 单调用降级；manifest 的 `fallback` 从布尔升级为“用户可见的降级承诺”。

三类中间形态不再靠试错：动态 UI 拆成 `UI_INJECT / UI_READ / UI_MUTATE` 三个能力；反射给出 dunder 守卫 + `api.reflect` 替代 API；跨插件给出 `api.plugins` + `api.data` 双端同意的显式契约，取代“猜目录、试文件”。

需要用户拍板的取舍集中在第 8 节，共 9 条。

## 1. 现状诊断（只读证据）

### 1.1 拒绝信号只有字符串

- 审计钩子的所有拦截最终都走 `_deny`，末尾固定为 `raise PermissionError(f"插件 '{owner_name}' {reason}{suffix}")`（`djs_pyqt6.py:6403`）。异常对象没有任何自定义属性。
- API 侧拦截走 `_deny_plugin_api`，同样是纯字符串 `PermissionError`（`djs_pyqt6.py:6798`）。
- 控件类密封在 `_seal_widget_class.__setattr__` 里调用 `require_permission`（`djs_pyqt6.py:6836-6841`），插件改类属性时收到的是同一形态的异常，看不出是“密封”而不是“没授权”。
- 硬拦模块导入抛 `ImportError`（`djs_pyqt6.py:7611`），与权限拒绝是两套异常体系，插件要写两个 `except`。

插件只能靠 `str(exc)` 猜。文案里没有任何稳定标识，改文案即等于破坏插件判断。

### 1.2 申请接口丢掉了结果结构

`PluginManager.request_permission()` 内部已经返回结构化字典（`ok / level / code / message / cooldown`，`djs_pyqt6.py:7189-7240`），但两条插件侧通道都把它压成布尔：

- 进程内：`PluginAPI.request_permission()` → `return bool(result.get("ok"))`（`djs_pyqt6.py:4835`）。
- 宿主：`HostPluginAPI.request_permission()` → `bool(self._runtime.request_permission(...).get("ok"))`（`djs_pyqt6.py:8799-8802`）。

于是 `undeclared / denied / cooldown / busy / rate_limited / timeout / cancelled` 七种完全不同的结局，在插件眼里都是 `False`。插件无法决定“该改走替代方案”还是“该提示用户去安全中心”。

### 1.3 已经存在、但插件看不见的事实

| 事实 | 现状位置 | 插件视角 |
| --- | --- | --- |
| 拒绝并记住 | `grants_v2` 的 `{"level":"deny"}`；`is_grant_denied`（`djs_pyqt6.py:7295`） | 只能通过 `permission_status()` 得到字符串 `deny`，没有时间、没有目标、没有“谁记的” |
| 保护区：应用配置 | `_is_protected_file`（`djs_pyqt6.py:7573`） | 只得到“应用内部配置文件受保护”一句话 |
| 保护区：插件源码 | `_is_plugin_source`（`djs_pyqt6.py:6565`）、`_is_own_source`（`djs_pyqt6.py:6689`） | 只能猜“为什么读同目录另一个 py 就不行” |
| 保护区：系统目录 | `_is_system_path`（`djs_pyqt6.py:6680`） | 需 `SYSTEM_INFO`，但异常不说这是“系统目录”子类 |
| 保护区：开机启动 | `_is_startup_path`（`djs_pyqt6.py:6671`） | 需 `AUTOSTART`，同上 |
| 硬拦 | `_ALWAYS_DENY`、`_BLOCKED_MODULES`（`djs_pyqt6.py:4994-5004`） | `ImportError` 或“禁止插件干预安全钩子”，没有 `unlockable=false` 标记 |
| 控件密封 | `seal_module_widgets`（`djs_pyqt6.py:6852`） | 静默替换类对象，反射看到的 `type()` 已变，失败时只有权限文案 |
| `once` 档位消耗 | `consume_once_for`（`djs_pyqt6.py:7299`） | 第一次放行后档位变 `none`，第二次突然被拒，插件无感知 |
| 询问冷却/限流 | `PROMPT_COOLDOWN=300`、`PROMPT_MAX_PER_WINDOW=4`（`djs_pyqt6.py:7097-7099`） | 与“用户拒绝”同为 `False` |
| 信任模式 | `is_plugin_trusted` 旁路（`djs_pyqt6.py:6494-6495`、`6532`） | 信任后范围检查被跳过，插件行为随用户设置漂移，自己不知道 |

### 1.4 判定本身是 fail-open 的几处

结构化拒绝必须建立在“判定只有一个出口”上，否则预检和实际执行会不一致。当前至少三处静默放行：

- 无法归属插件且栈里也没有插件帧时直接 `return`（`djs_pyqt6.py:6359-6360`）。
- `_require_permission` 在 `plugin is None`、`_audit_suppress=True`、`_audit_guard.active=True` 时直接返回 `False`（`djs_pyqt6.py:6809-6818`），而 `PluginAPI._require` / `HostPluginAPI._require` 只把它当返回值丢弃（`djs_pyqt6.py:4697`、`8683`）——注册类 API 在抑制窗口内等于免检。
- 通知/服务/内容提供者等注册通道没有权限检查（`djs_pyqt6.py:8834-8863`）。

这三处不修，“预检说不行、实际放行”或反过来都会发生，用户解释会自相矛盾。

### 1.5 用户侧“有权限≠能做”缺一层归因

授权状态在 UI 里表现为位图（`persistent_permissions` 等），但拦截的真实原因分布在四层加上一个放宽模式：清单声明（L1）、授权档位（L2）、保护区（L3）、硬性规则（L4），以及“信任模式跳过 L3”这一事实。安全中心目前把它们压成同一句“拦截”，用户无法分辨“我明明给了权限”。

### 1.6 三类中间形态的现状

- 动态 UI：所有注册面都只查 `UI_INJECT`（`djs_pyqt6.py:4713`、`4740`、`8720-8782`），但“注册界面”“读取宿主界面结构”“改写宿主/插件控件类”是三种风险，共用一个位；进程内模式还直接持有 `PluginAPI._app`，可绕过插槽契约。
- 反射：宿主内置白名单包含 `getattr / setattr / dir / vars / type / object / eval / exec`（`djs_pyqt6.py:8599-8608`），`inspect` 在禁模块名单里；结果是合法自省无路可走、越界自省也无人拦，异常只会在别处以权限拒绝的形式出现。
- 跨插件：`provide_service / call_service` 无需权限（`djs_pyqt6.py:8838-8855`），且 `call_service` 会把上下文切到**提供方**（`djs_pyqt6.py:8843-8848`），调用方在服务里做的文件操作被记到对方账上；跨插件读源码需 `PLUGIN_SOURCE`，跨插件读写数据没有公开 API，只能猜目录然后撞保护区。

## 2. 四层归因模型（全方案共用词汇）

用户和插件看到的是同一套层号，避免“插件文档说 A、界面说 B”。

| 层 | 名称 | 管什么 | 典型判定 | 可否由用户放开 |
| --- | --- | --- | --- | --- |
| L1 | 声明层 | 清单里有没有这项能力 | `undeclared` | 否（只能改清单） |
| L2 | 授权层 | 用户给了什么档位 | `not_granted`、`remembered_deny`、`cooldown`、`rate_limited`、`busy`、`timeout` | 是 |
| L3 | 范围层 | 已授权，但目标是保护区 | `zone.protected_file`、`zone.system`、`zone.startup`、`zone.plugin_source` | 是（授权对应保护区权限/换目录） |
| L4 | 强制层 | 无论授权都不放开 | `hard.blocked_module`、`hard.security_hook`、`hard.dunder_access`、`hard.disabled`、`origin.unknown_plugin`、`seal.widget_class` | 否 |

一句话心智模型（用于帮助页与安全中心顶部说明）：

> 插件要做的事，先在它声明的范围里被允许（L1），再需要你给过授权（L2），还要落在允许的位置（L3）；L4 是保护宿主与安全机制本身的硬规则，不开放。

`trust_bypass` 不是拒绝，而是一个可见的“放宽事实”：信任模式下 L3 检查被跳过。它必须出现在 `capabilities()` 与安全中心里，否则用户会以为“同样的操作有时能、有时不能”。

## 3. 结构化拒绝契约

### 3.1 异常类型

新增两个异常，均位于 `djs_pyqt6.py` 顶层，插件可直接从 `djs_pyqt6` 导入：

```python
class PluginPermissionDenied(PermissionError):
    code: str
    permission: str
    permission_bit: int
    capability: str
    scope: dict
    denied_by: str
    layer: str
    retryable: bool
    unlockable: bool
    unlock_action: str
    retry_after_ms: int
    origin: str
    plugin: str
    operation: str
    target: str
    message: str
    details: dict

class PluginHardBlockDenied(PluginPermissionDenied, ImportError):
    pass
```

约定：

- 继承 `PermissionError`，所有现有 `except PermissionError` 无需改动。
- 硬拦模块导入使用 `PluginHardBlockDenied`，同时满足 `except ImportError`。
- `str(exc)` 返回 `message`，与现有文案同形，旧日志不变。
- 新增 `exc.to_dict()`，字段全部 JSON 安全，可直接写日志、上报或序列化。
- 异常**只在进程内**抛出，不跨宿主 IPC；跨进程只传第 5 节的快照与事件。

### 3.2 字段语义

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | str | 稳定机器码，插件分支只认它，不认文案 |
| `permission` | str | 权限位名，如 `FILE_WRITE`；无法归属时为 `""` |
| `permission_bit` | int | 位值，便于按位组合判断 |
| `capability` | str | 被拒的具体能力，如 `file.write`、`widget.class.setattr`、`service.call` |
| `scope` | dict | `{"kind":"path"|"domain"|"module"|"widget"|"plugin"|"none","value":str,"zone":str}` |
| `denied_by` | str | 规则来源：`manifest / grant / zone / hard / seal / host` |
| `layer` | str | `L1`..`L4`，与第 2 节一致，供 UI 直接显示 |
| `retryable` | bool | 同样的调用原样重试是否可能成功 |
| `unlockable` | bool | 用户是否有可能通过授权放开 |
| `unlock_action` | str | 可执行的解锁入口，如 `security_center.permissions`、`security_center.cross_plugin`、`""` |
| `retry_after_ms` | int | 冷却/限流剩余毫秒，`0` 表示无限制 |
| `origin` | str | `audit / api / seal / import / env / clipboard / thread / service` |
| `plugin` | str | 插件文件名 |
| `operation` | str | 审计事件名或 API 名 |
| `target` | str | 目标路径/域名/类名，截断到 120 字符 |
| `details` | dict | 补充信息：`zone`、`candidates`（网络权限合并项）、`trusted`、`once_remaining` |

`scope.zone` 只出现在 L3，取值：`app_config`、`plugin_source`、`system`、`startup`。

需要特别说明：当前白名单（`is_path_whitelisted`，`djs_pyqt6.py:7440`）是**放行捷径**，不是限制边界——命中白名单且未被“拒绝并记住”时直接放行，未命中白名单也仍然按权限位判定。本方案不改变这个语义；把 `FILE_WRITE` 改成“按目录授权”属于方向性收紧，见 8.4 的否决项。因此 L3 的真实来源只有保护区，而不是“没加白名单”。

### 3.3 `code` 枚举（完整表）

| code | layer | denied_by | retryable | unlockable | 含义 |
| --- | --- | --- | --- | --- | --- |
| `perm.undeclared` | L1 | manifest | 否 | 否 | 清单未声明该权限 |
| `perm.not_granted` | L2 | grant | 是（用户可弹窗） | 是 | 已声明，未授权 |
| `perm.remembered_deny` | L2 | grant | 否 | 是 | 用户选择“拒绝并记住” |
| `perm.cooldown` | L2 | grant | 是（等待） | 是 | 询问冷却中 |
| `perm.rate_limited` | L2 | grant | 是（等待） | 是 | 询问过于频繁被静默 |
| `perm.busy` | L2 | grant | 是 | 是 | 另一询问进行中 |
| `perm.timeout` | L2 | grant | 是 | 是 | 用户未在时限内响应 |
| `perm.cancelled` | L2 | grant | 是 | 是 | 用户取消 |
| `zone.protected_file` | L3 | zone | 否 | 否 | 应用配置/密钥文件 |
| `zone.plugin_source` | L3 | zone | 是（需授权） | 是 | 改写或读取他人插件源码 |
| `zone.system` | L3 | zone | 是（需授权） | 是 | 系统目录 |
| `zone.startup` | L3 | zone | 是（需授权） | 是 | 开机启动目录/Run 键 |
| `hard.blocked_module` | L4 | hard | 否 | 否 | 危险模块硬拦 |
| `hard.security_hook` | L4 | hard | 否 | 否 | 干预审计/调试接口 |
| `hard.dunder_access` | L4 | hard | 否 | 是（`DANGEROUS_EVAL`） | 反射访问逃逸 dunder |
| `hard.disabled` | L4 | hard | 否 | 是（重新启用） | 插件或全局被禁用 |
| `seal.widget_class` | L4 | seal | 否 | 是（`UI_MUTATE`） | 控件类被密封 |
| `origin.unknown_plugin` | L4 | host | 否 | 否 | 无法归属到具体插件 |
| `host.service_denied` | L4 | host | 否 | 视配置 | 服务不存在或未对调用方开放 |
| `host.export_denied` | L4 | host | 否 | 否 | 对方未导出该数据/源码 |
| `ok.granted_retry` | L2 | grant | 是（立即） | 不适用 | 拦截后询问已授权，应立即重试 |

`ok.granted_retry` 对应当前 `_deny` 里的 `retry` 分支（`djs_pyqt6.py:6392`、`6402`）：对话框已授权，但异常仍然抛出，只多一句“请重试”。这是插件最难处理的形态——**它既不是成功也不是失败**。结构化后必须单独标出，`retryable=True`、`retry_after_ms=0`，并建议实现改为“授权成功则不抛异常、直接执行原操作”，见 8.1。

### 3.5 兼容性边界

- 文案（`message`）保持现有中文句式，不改变旧插件的日志可读性。
- 异常仍是 `PermissionError` 子类；`except PermissionError as e: print(e)` 行为不变。
- `ImportError` 分支双继承后，`except ImportError` 仍命中。
- 新增属性是纯附加；不改变任何现有调用的成功/失败结论。

## 4. 插件侧自省与降级

### 4.1 `api.capabilities()`：一次拿到全部事实

进程内与宿主两套 API 都必须提供同名方法，宿主通过新增 IPC 方法 `capabilities` 拉取快照。宿主协议版本从 2 升到 3（`_PLUGIN_HOST_PROTOCOL`，`djs_pyqt6.py:8339`）；清单里写 `api_version: 3` 的插件在旧宿主上会被拒绝加载（`djs_pyqt6.py:9598`），这是有意为之，避免插件以为能拿到新 API 却拿到空值。

### 4.2 `api.can()`：申请前可查

```python
def can(self, permission, target=None, event=""):
    ...
```

- 返回值是 `Decision` 字典：`{"ok": bool, "code": str, "layer": str, "scope": dict, "retryable": bool, "unlockable": bool, "reason": str}`，字段与异常同构，但不抛异常。
- 语义严格对应真实执行：文件类要传 `target`，服务类要传 `event="service.call"`，密封类传 `event="widget.class.setattr"`。
- **无副作用**：不弹窗、不写审计、不计数、不消耗 `once`、不触发冷却、不通知托盘。
- 与执行共用同一个纯评估器（第 6 节），保证“预检说能，执行就能”。

典型用法：

```python
if not self.api.can(PluginPermission.FILE_WRITE, target=path)["ok"]:
    self.api.log("跳过导出：目标不在允许范围", "INFO")
    return self._export_to_clipboard()
```

### 4.3 `api.explain()`：给用户看的句子

```python
def explain(self, permission, target=None, event=""):
    ...
```

返回 `{"layer": "L3", "title": "...", "detail": "...", "action": "...", "code": "zone.system"}`。插件可以把它原样放进自己的错误提示，用户看到的是与安全中心一致的层号与解释，不会出现“插件说权限不足、安全中心说范围受限”的对不上。

### 4.4 `request_permission` 返回结构化结果

三种可选实现，按兼容强度排序：

| 方案 | 形态 | 兼容性 | 风险 |
| --- | --- | --- | --- |
| A | 返回 `PermissionResult`，实现 `__bool__` | `if api.request_permission(...)` 不变 | 旧代码若写 `is True` / `== True` 会失效 |
| B | 保留布尔，新增 `request_permission_v2()` | 完全兼容 | 插件作者要学新方法，旧方法继续误导 |
| C | 返回布尔，同时通过 `api.last_denial()` 取失败详情 | 完全兼容 | 有状态、并发不安全，插件要立刻读 |

建议 **A + C 兜底**：`PermissionResult` 提供 `.ok / .level / .code / .denial / .retryable / .unlockable`，同时实现 `__bool__` 和 `__eq__`（与 `True/False` 比较仍成立）。这是本方案里唯一“可能影响现有插件语义”的接口变更，需用户拍板（8.2）。

### 4.5 声明式降级：manifest 扩展

`permissions_v2.on_demand` 每项由：

```json
{"perm": "FILE_WRITE", "feature": "导出", "reason": "把结果写到用户选择的文件"}
```

扩展为（新增字段全部可选，旧清单不受影响）：

```json
{
  "perm": "FILE_WRITE",
  "feature": "导出",
  "reason": "把结果写到用户选择的文件",
  "required": false,
  "fallback": {
    "mode": "alternate",
    "hint": "没有写文件权限时，改为复制到剪贴板",
    "code": "EXPORT_CLIPBOARD"
  }
}
```

`fallback` 的两种形态都接受：

- 旧形态 `true/false`：保持现在语义（仅对 `FALLBACK_ALLOWED` 的网络与剪贴板开放“拦截后询问”）；
- 新形态对象：`mode ∈ skip | alternate | ask | readonly`，`hint` 是**给用户看的承诺**（“你不给这项权限，插件会怎样”），`code` 是插件内部降级分支标识。

`required: true` 表示没有它插件无法工作：宿主在审批时把该插件标为“必需项”，拒绝后安全中心显示“插件将不可用”，而不是让插件跑到一半崩掉。

`fallback.hint` 进入权限弹窗与安全中心，解决用户“给了权限却不知道换来了什么”的问题；它同时是插件对用户的书面承诺，后续若插件并未按 hint 降级，属于插件质量问题而非权限模型问题。

### 4.6 运行时降级 API

```python
def on_denial(self, callback):
    ...

def call_with_fallback(self, permission, primary, fallback=None, target=None, event=""):
    ...

def declare_degraded(self, permission, reason, action):
    ...

def last_denial(self):
    ...
```

- `on_denial(cb)`：任何来源（审计、密封、API、导入）的拒绝都会回调一次，参数是 `Decision`。插件可在回调里把功能开关关掉、给用户一条说明，而不是等着下一次崩溃。
- `call_with_fallback()`：先 `can()`；能则执行 `primary`；不能则执行 `fallback`，并把 `Decision` 作为参数传给 `fallback`，让降级分支知道具体原因。这是把“失败即中断”变成“失败可降级”的最小改动面。
- `declare_degraded()`：登记“本插件当前以受限模式运行”，安全中心与插件管理页显示“受限：缺少 FILE_WRITE，已降级为剪贴板导出”。这是给用户看的运行时事实，不是日志。

### 4.7 建议的插件写法（示意）

```python
def export(self, rows, path):
    decision = self.api.can(PluginPermission.FILE_WRITE, target=path)
    if decision["ok"]:
        with open(path, "w", encoding="utf-8") as f:
            f.write(self._render(rows))
        return "file"
    self.api.log(f"降级导出：{decision['code']} / {decision['layer']}", "INFO")
    self.api.declare_degraded(PluginPermission.FILE_WRITE,
                              decision["reason"], "复制到剪贴板")
    QApplication.clipboard().setText(self._render(rows))
    return "clipboard"
```

这段写法不依赖异常，也不依赖任何中文文案。

## 5. 让“被记住的拒绝、保护区、密封”成为插件可见事实

### 5.1 落盘结构扩展（`grants_v2`）

现有条目只有 `level`（`djs_pyqt6.py:7493-7513`、`7341-7368`）。扩展为：

```json
{
  "plugin.py": {
    "2": {
      "level": "deny",
      "since": "2026-11-05 19:02:11",
      "denied_at": "2026-11-06 21:14:02",
      "denied_count": 3,
      "last_code": "zone.system",
      "last_target": "C:\\Windows\\System32\\drivers\\etc\\hosts",
      "denied_source": "security_center"
    }
  }
}
```

- `denied_count` 只统计“同一权限被拒次数”，用于 UI 折叠与“为什么总被拦”排序。
- `last_code / last_target` 让 `capabilities()` 能回答“为什么”，而不只是“拒绝了”。
- 写入点统一：`_deny`、`_deny_plugin_api`、`set_grants_bulk`。仍然只在拒绝发生与用户操作时写盘，不因预检写盘。

### 5.2 `permission_state()` 取代只读字符串

保留 `permission_status()` 原样（返回 `none/once/session/permanent/deny`），新增：

```python
def permission_state(self, permission):
    ...
```

返回 `{"level","status","since","denials":{...},"unlockable","unlock_action"}`。旧插件不受影响，新插件能拿到时间与原因。

### 5.3 拒绝事件回传插件

宿主目前只把 `denied` 发给父进程弹提示（`djs_pyqt6.py:8651-8652`、`5705-5715`）。改为：

- 新增 IPC 事件 `permission_denied`，参数为 `Decision`（去掉本地化文案，保留 `code/layer/target`）；
- `PluginHostRuntime` 收到后分发给对应插件的 `on_denial` 回调；
- 父进程的安全中心订阅同一份数据，作为“拦截记录”的来源。

这样同一次拒绝，插件与用户看到的是同一条事实，不会一边只有日志、一边只有托盘。

### 5.4 密封事实可见

- `capabilities().limits.sealed_widgets` 列出本插件被密封的类名。
- 密封发生在模块加载后（`djs_pyqt6.py:7779`、`9581`），插件可在 `on_enable` 里读取该字段。
- `_seal_widget_class` 拒绝时抛 `seal.widget_class`，`unlockable=True`（对应新权限 `UI_MUTATE`），而不是复用“无界面注入权限”（那会让插件误以为没给 `UI_INJECT`）。
- 实例属性不受限，只有类属性/类方法改写受限；这一点必须写进帮助页，否则插件作者会以为“反射全禁”。

### 5.5 用户可见的联动

安全中心（`PluginSecurityCenterDialog`，`djs_pyqt6.py:29751`）新增两处：

1. 权限行增加第四列“限制来源”，值为 `声明 / 授权 / 范围 / 强制`，悬浮显示 `last_code` 对应的原因句；
2. 插件详情顶部增加一行摘要：`N 项已授权 · M 项范围受限 · K 项已拒绝 · J 项硬性限制`，点击任一数字跳到对应行。

拦截卡（`SecurityNoticeCard`，`djs_pyqt6.py:30986`）标题改为“已拦下 1 项”，正文首行为插件名与动作，第二行固定为层号 + 原因短句，第三行是动作按钮（见 6.3）。

## 6. 面向用户：让“有权限但做不了”可解释

### 6.1 不新增概念，只新增一个后缀

顶层状态仍然是二元的“已授权 / 未授权”。当已授权但被 L3 拦过，显示为：

> **已授权（范围受限）**

这是唯一的词汇增量。用户不需要理解“保护区”“作用域”这些词，只需要知道“权限给了，但位置不对”。点开后才有细节。

触发条件很具体：**已授权 + 目标是保护区**（应用配置、系统目录、开机启动目录、他人插件源码）。普通目录不会出现这个后缀。

### 6.2 六种状态的固定话术

| status | 界面用词 | 一句话解释 | 主按钮 |
| --- | --- | --- | --- |
| `granted` | 已授权 | 插件可以使用这项能力 | 撤销 |
| `granted_scoped` | 已授权（范围受限） | 权限已给，但目标属于保护区（系统/启动目录、他人插件、应用配置） | 查看范围 |
| `denied_remembered` | 已拒绝并记住 | 你之前选了“不再询问”，不会再弹窗 | 改为询问 |
| `not_granted` | 未授权 | 插件声明了这项能力，你还没给 | 授权 |
| `undeclared` | 未声明 | 插件清单里没有这项，请求会被直接拒绝 | 无 |
| `hard_limited` | 系统限制 | 这一项不对外开放，授权也不会生效 | 为什么 |

### 6.3 拦截通知模板

固定三段，不超过三行：

```text
「插件名」想写入 C:\Windows\System32\drivers\etc\hosts，被保护区规则拦下。
已授权写入文件，但该路径属于系统目录，需要单独的设备信息授权（L3）。
[查看允许范围] [查看规则]
```

L1 到 L4 的固定句式：

| 层 | 句式 | 按钮 |
| --- | --- | --- |
| L1 | 插件没有声明这项能力，宿主直接拒绝。 | 联系作者 / 无 |
| L2 | 你还没有授权，或之前选择了拒绝并记住。 | 去授权 / 改为询问 |
| L3 | 权限已给，但这个位置不在允许范围。 | 加入允许范围 / 换目录 |
| L4 | 这是保护宿主与安全机制的硬规则，不开放。 | 为什么 |

L4 的“为什么”打开帮助页对应段落，而不是再弹一个对话框。

### 6.4 权限页的第二行信息

每个权限项展开后只多两行：

- `能做什么`：直接取 `_PERM_SPECS[flag]["scope"]`（`djs_pyqt6.py:4425-4486`），文案已存在。
- `拦过什么`：取 `denials` 的最近一条，格式为 `2026-11-06 写入 C:\Windows\System32\drivers\etc\hosts · 系统目录`，点击跳到审计记录。

没有拦截历史时不显示第二行，避免默认界面变复杂。

### 6.5 避免新的心智负担

- 不向用户暴露 20 个权限位的位图；只暴露“项”和“状态”。
- 不在主界面新增第五个标签页；“限制来源”是权限表的列，不是新页面。
- 所有新解释都从既有故障点进入（拦截卡、权限行、审计记录），用户不主动学习也能遇到。
- “已授权（范围受限）”必须给出可执行出路：换到普通目录，或授权对应的保护区权限（`SYSTEM_INFO` / `AUTOSTART` / `PLUGIN_SOURCE`），并在卡片上直接给按钮，而不是只显示一个词。

## 7. 三类中间形态：明确能力划分与替代 API

### 7.1 动态 UI

**能力拆分**（新增位一律追加在 20 位之后，不改变现有位值）：

| 能力 | 位 | 风险 | 基线 | 管什么 |
| --- | --- | --- | --- | --- |
| `UI_INJECT` | 既有 | 2 | 是 | 注册界面插槽：设置页/面板/悬浮控件/卡片/皮肤/工具栏按钮 |
| `UI_READ`（新） | 追加 | 2 | 否 | 读取宿主界面结构：窗口列表、主题 token、已注册插槽清单 |
| `UI_MUTATE`（新） | 追加 | 3 | 否 | 改写宿主控件或插件控件类：类属性注入、运行时 monkeypatch、跨插件控件替换 |

规则：

- 只有 `UI_INJECT` 时，注册插槽可用；对宿主对象只能通过 `api.host` 门面读取公开属性，不能直接持有 `_app`。
- 进程内 `PluginAPI` 目前把 `self._app` 暴露给插件（`djs_pyqt6.py:4675` 起）；改为 `api.host` 只暴露 `slots / theme / windows_meta / register_*` 四组，`_app` 在 2 个 minor 版本后移除。这是行为变更，见 8.5。
- 类属性注入走 `UI_MUTATE`，未授权时抛 `seal.widget_class`，而不是“无界面注入权限”。
- 替代 API（避免 metaclass 冲突）：

```python
def bind_behavior(self, widget_class, name, func):
    ...

def slots(self):
    ...
```

`bind_behavior` 是“给控件类注入方法”的官方路径：它把方法挂到密封类的**实例**查找表上（`__getattr__` 兜底），不触发类属性写，因此不需要绕过密封，但仍然按 `UI_MUTATE` 审计。

**兼容性**：只注册插槽的现有插件完全不受影响；只有做运行时类改写的插件需要补声明 `UI_MUTATE`（当前这类插件在无 `UI_MUTATE` 时仍可写类属性，因为只查 `UI_INJECT`，所以这是“收紧”，需在版本说明里写清）。

### 7.2 反射

**现状**：`getattr / setattr / dir / vars / type / object / eval / exec` 全部可用（`djs_pyqt6.py:8599-8608`），`inspect` 被禁；dunder 逃逸（`__subclasses__`、`__globals__`、`__code__`）没有任何拦截，因为审计钩子看不到属性访问。

**设计**：

1. 在宿主与进程内两套 builtins 里把 `getattr / setattr / vars / type` 换成守卫版本（与 `_host_safe_builtins` 同一处装配）。
2. 守卫名单：`__subclasses__`、`__globals__`、`__code__`、`__bases__`、`__mro__`、`__builtins__`、`__loader__`、`__spec__`、`__reduce__`、`__getstate__`。
3. 命中时抛 `PluginPermissionDenied`，`code="hard.dunder_access"`（建议补入 3.3 表），`layer="L4"`，`retryable=False`，`unlockable=True`（仅 `DANGEROUS_EVAL`）。
4. 放行 `__dict__` 读取、`__class__` 读取、`__name__`、`__doc__`、`__module__`，避免打断正常自省与 Qt 代码。
5. 替代 API：

```python
def describe(self, obj, depth=1):
    ...

def members(self, obj, public_only=True):
    ...

def signature(self, func):
    ...
```

`signature` 填上 `inspect` 被禁后的空缺，返回参数名、默认值、注解，不返回源码对象。

**兼容性**：用 `type(x).__mro__` 做类型判断的插件会受影响（少见）；用 `obj.__class__` 的不受影响。这是“安全 vs 自由度”的直接取舍，见 8.3。

### 7.3 跨插件读写

**现状问题**：服务通道开放但无同意、归属错位；数据通道不存在，只能猜目录。

**设计：双端同意 + 显式命名空间**

新权限位：

| 能力 | 风险 | 基线 | 管什么 |
| --- | --- | --- | --- |
| `PLUGIN_CALL`（新） | 2 | 否 | 调用其他插件提供的服务 |
| `PLUGIN_DATA_SHARE`（新） | 3 | 否 | 读写其他插件导出的数据命名空间 |
| `PLUGIN_SOURCE` | 既有 | 3 | 读取其他插件源码 |

提供方在 manifest 里声明导出：

```json
{
  "exports": {
    "services": [{"name": "render_chart", "public": false, "reason": "为其他插件提供图表渲染"}],
    "data": ["shared/**"],
    "source": false
  }
}
```

调用方 API：

```python
def plugins(self):
    ...

def call(self, plugin, service, *args, **kwargs):
    ...

def data_read(self, plugin, relpath):
    ...

def data_write(self, plugin, relpath, payload):
    ...
```

规则：

- `plugins()` 列出插件名、版本、公开服务；需要 `PLUGIN_CALL`，返回体不含私有服务名。
- `call()` 需要 `PLUGIN_CALL`，且对方服务 `public=true` 或用户在安全中心为该组合授权一次；否则抛 `host.service_denied`，`unlockable=true`，`unlock_action="security_center.cross_plugin"`。
- `data_read / data_write` 需要 `PLUGIN_DATA_SHARE`。当前版本没有实现 `exports.data` 文件共享接口，该权限位仅作预留；跨插件通信使用公开服务或事件。
- 直接文件读写他人数据目录仍然禁止（`_is_plugin_source` 与保护区逻辑不变），新 API 是唯一合法通道。
- 归属修正：`call_service` 维护 `service_chain`，审计记录同时带 `plugin`（提供方）与 `delegated_by`（调用方）；调用方在服务内做的文件操作按**调用方**权限判定，不借用提供方权限。这是安全语义变更，见 8.4。

**替代路径的价值**：插件不再需要 `os.listdir(其他插件目录)` 或猜 `data/` 下的文件名，也就不会撞上“保护区/未知插件”这种既拿不到能力又拿不到理由的模糊地带。

## 8. 行为变更、兼容性与需要拍板的取舍

### 8.1 变更清单

| # | 变更 | 类型 | 对现有插件 | 需拍板 |
| --- | --- | --- | --- | --- |
| 1 | 拒绝异常附带结构化字段，仍是 `PermissionError` | 附加 | 无影响 | 否 |
| 2 | 硬拦导入改双继承 `PermissionError + ImportError` | 附加 | `except ImportError` 仍命中 | 否 |
| 3 | `request_permission` 返回 `PermissionResult`（bool 兼容） | 语义 | 极少数 `is True` 判断会失效 | 是（Q2） |
| 4 | 拦截后询问已授权时，不再抛异常而是直接继续 | 语义 | 插件少一次“重试”分支，行为更顺 | 是（Q1） |
| 5 | `grants_v2` 增加拒绝时间/原因/次数字段 | 附加 | 无影响 | 否 |
| 6 | `permission_state()`、`capabilities()`、`can()`、`explain()` 新增 | 附加 | 无影响 | 否 |
| 7 | deny 记忆、保护区、密封进入插件可见事实 | 附加 | 无影响（插件可选择不读） | 否 |
| 8 | 判定重构为纯评估器 + 副作用执行器 | 内部 | 理论上无影响，需金标用例兜底 | 否 |
| 9 | 安全中心新增“限制来源”列与摘要行 | UI | 无影响 | 否 |
| 10 | 新增 `UI_READ`、`UI_MUTATE`、`PLUGIN_CALL`、`PLUGIN_DATA_SHARE` 四位 | 扩展 | 旧清单不受影响；位值追加在末尾 | 是（Q6） |
| 11 | 类属性改写从“查 `UI_INJECT`”改为“查 `UI_MUTATE`” | 收紧 | 做运行时类改写的插件需补声明 | 是（Q6） |
| 12 | `PluginAPI._app` 收口为 `api.host` 门面 | 收紧 | 进程内模式下直接读 `_app` 的插件会失效 | 是（Q5） |
| 13 | dunder 反射守卫 | 收紧 | 用 `__mro__/__subclasses__` 的插件会失效 | 是（Q3） |
| 14 | 跨插件服务需 `PLUGIN_CALL`，且默认私有 | 收紧 | 现有跨插件调用需补声明或用户授权 | 是（Q4） |
| 15 | 服务调用归属不再借用提供方权限 | 修正 | 依赖“借权限”的插件会暴露真实权限缺口 | 是（Q4） |
| 16 | 保护判定 fail-open 三处改为 fail-closed / 结构化放行 | 修正 | 依赖静默放行的插件会开始被拦 | 否（安全必需） |
| 17 | `_PERM_NAMES` 与 `_PERM_LABELS` 合并 | 内部 | 无影响 | 否 |

第 16 条是安全前提，但如果现有插件依赖“无法归属时放行”，升级后会开始报错。建议在 P0 阶段加一个“观察模式”：仍放行，但记录 `origin.unknown_plugin` 到安全中心，连续两个小版本后再收紧。这样既不破坏，也不永久失守。

### 8.2 需要拍板的九个取舍

| # | 问题 | 选项 | 推荐 | 影响面 |
| --- | --- | --- | --- | --- |
| Q1 | 拦截后询问已授权，重启原操作还是抛异常 | A 直接继续 / B 保持抛异常 + `ok.granted_retry` | A | 插件代码更简单；审计需要记录“一次拦截一次放行” |
| Q2 | `request_permission` 返回值 | A 兼容布尔的结果对象 / B 新增 v2 方法 / C 布尔 + `last_denial()` | A + C | 唯一可能影响旧代码语义的改动 |
| Q3 | dunder 反射 | A 硬禁（需 `DANGEROUS_EVAL` 解锁）/ B 只记录不拦 | A | 安全收益大，少数插件需改写法 |
| Q4 | 跨插件默认同意模型 | A 默认私有，用户可授权 / B 默认公开，提供方可关闭 | A | A 更安全，但首次调用会多一次询问 |
| Q5 | `_app` 收口 | A 2 个 minor 后移除 / B 保留只读代理 | A | 进程内模式插件需迁移；宿主模式本就没有 |
| Q6 | 新增 4 个权限位 | A 接受 / B 只加 `PLUGIN_CALL`，UI 用事件细分 | A | 位越多，授权界面越需要分组，但能力边界更清楚 |
| Q7 | 是否允许插件主动唤起安全中心申请解锁 | A 允许（带冷却与频控）/ B 只允许用户主动进入 | A | 便利，但需要防骚扰 |
| Q8 | 是否把保护区/系统目录清单下发给插件 | A 下发（只给路径，不给内容）/ B 只给布尔判定 | A | 预检才可能准确；路径本身不是秘密 |
| Q9 | 是否把 `FILE_WRITE` 从“全局能力”改为“按目录授权” | A 保持全局 + 保护区兜底 / B 按目录逐个授权 | A | B 会让几乎所有现有插件失效，与本轮目标相反，本轮不做 |

### 8.3 破坏性风险排序

1. **跨插件服务收紧（14/15）**：会直接让现有调用失败，且失败点在运行期。缓解：先发“观察模式”，把无声明调用记为 `host.service_denied` 但不拦，一个版本后再拦。
2. **`_app` 收口（12）**：只在关闭插件宿主时出现，影响面小但报错突兀。缓解：先保留 `_app` 但返回只读代理，写入时抛结构化拒绝。
3. **反射守卫（13）**：命中面窄，但一旦命中就是 `AttributeError` 变 `PermissionError`，插件可能没写对应 `except`。
4. **`UI_MUTATE` 拆分（11）**：只有做类改写的插件受影响，可通过 `capabilities().features["ui.mutate"]` 提前判断。
5. **`request_permission` 语义（3/4）**：最容易被旧代码以 `is True` 形式误判，需在版本说明里单列。

### 8.4 不做什么

- 不把白名单改造成限制边界，也不把 `FILE_WRITE` 改为“按目录授权”。当前 `FILE_WRITE` 是全局能力、保护区兜底，这是“守规矩的插件更自由”的前提；一旦改成逐目录授权，现有插件会大面积失效。
- 不改 `permissions` 旧整数格式的迁移规则（`parse_permission_manifest`，`djs_pyqt6.py:4555-4645`）。
- 不改 `once / session / permanent / deny` 四档语义，只补可见性。
- 不新增第五个授权档位。
- 不把预检做成“自动授权”；`can()` 永不弹窗、永不改状态。
- 不动审计钩子的拦截结论，只把结论结构化。

### 9.2 验收用例（可直接扩展现有测试插件）

复用 `D:\GuZhi\plugins\permission_stage_probe.py`，增加断言行：

第 13 条是判定重构的回归闸门：只要预检与执行出现分歧，说明还有第二套判定逻辑没收敛。

### 9.3 验收脚本与不变量

- `py_compile` 通过，主程序不重启用户实例。
- 每次拒绝只产生一条审计记录、一张通知卡（去重按 `(plugin, code, target)`）。
- `capabilities()` 不写盘、不弹窗、不改变状态。
- 敏感信息：`limits` 只给路径名单，不读文件内容；`denials.last_target` 截断 120 字符。
